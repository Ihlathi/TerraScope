# TerraScope
## General-Purpose Robotics Telemetry, Visualization, Debugging, and Replay

### Project Vision

TerraScope is an open-source, framework-independent platform for
robotics telemetry, visualization, recording, debugging, and analysis.

Built upon AdvantageScope, TerraScope aims to preserve the existing
application's strengths while extending its capabilities to support
virtually any robot, sensor, hardware platform, programming language,
or robotics software framework.

TerraScope should provide a unified environment for understanding
the behavior of robotic and other engineering systems, both in real
time and through recorded data.

The ultimate goal is to make the underlying robotics software stack
largely irrelevant to the debugging and visualization experience.

---

# 1. Core Principles

- [x] Preserve existing AdvantageScope functionality and compatibility.
- [ ] Remain independent of any specific robotics framework. (Built around WPILib, AdvantageKit, FTC Dashboard, CTRE Phoenix, and REV logs.)
- [ ] Support arbitrary hardware architectures and computing platforms. (Desktop builds target Windows, macOS, and Linux on x64 and ARM.)
- [ ] Support telemetry generated by any programming language. (Any language that writes a supported log or speaks NetworkTables 4. No language-neutral protocol beyond those formats.)
- [x] Support multiple communication protocols and recording formats.
- [ ] Maintain consistent functionality between live and recorded data. (The same tabs read both. Phoenix and low-bandwidth NetworkTables only supply active fields.)
- [ ] Allow new functionality without requiring extensive core modifications. (Readers and custom schemas have an in-process registration API. Live sources and views still require core edits.)
- [x] Prioritize usability without limiting advanced capabilities.
- [ ] Support both robotics-specific and general engineering applications. (Line graphs and CSV import work on generic numbers. Field, swerve, and joystick views assume robot data.)
- [ ] Maintain high performance with large or high-frequency datasets. (WPILOG uses a WASM index and lazy field decode. The whole file is still read into memory.)
- [ ] Minimize the impact of telemetry collection on robot operation. (NetworkTables has a low-bandwidth subscription mode. Collection itself is robot-side.)
- [ ] Remain usable without an internet connection. (Local logs, live robot data, and embedded docs work offline. Video download, updates, and asset fetches use the network.)
- [x] Provide cross-platform compatibility.
- [ ] Remain open-source and community-extensible. (BSD-licensed source with custom assets and a compiled reader and custom schema API. Other extension types remain internal.)
- [x] Avoid unnecessary dependencies on external services.
- [x] Avoid requiring users to convert existing recordings.
- [x] Avoid forcing users to adopt a specific logging framework.
- [x] Make commonly needed capabilities available without custom plugins.
- [ ] Preserve access to raw data alongside interpreted representations. (Raw bytes are stored and structured types expand into child fields. There is no hex viewer.)
- [ ] Make data sources, transformations, and timestamps understandable. (Sidebar metadata, unit labels, and a timestamp display mode. Transformations are not recorded as a provenance trail.)
- [ ] Support reproducible debugging and analysis. (Saved layouts and AdvantageKit real/replay metadata. Analysis steps are not a reproducible pipeline.)

# 2. Data Sources and Recording Formats

## File-Based Data Sources

- [x] WPILOG support.
- [ ] MCAP support. (Export of scalar fields only. Hoot files are converted to WPILOG rather than opened as generic MCAP.)
- [ ] ROS 1 bag support.
- [x] ROS 2 sqlite3 bag support. (Single `.db3` files, CDR with embedded ROS message definitions or bundled common ROS 2 Humble definitions.)
- [ ] Additional ROS 2 bag storage and packaging. (Split bags, compressed bags, and directory metadata are not supported.)
- [ ] CSV and TSV support. (Comma-separated import and CSV export. Tab-separated files are not parsed.)
- [ ] JSON and JSONL support. (JSON values inside WPILOG, NetworkTables, and FTC Dashboard messages. JSON and JSONL files are not a log format.)
- [ ] Protobuf-based recordings. (Protobuf fields inside WPILOG and NetworkTables via ProtoDecoder. Generic protobuf files are not a log format.)
- [x] Structured binary recording formats.
- [ ] Human-readable application log formats. (The console tab renders timestamped text fields, including WPILib console structs. Standalone text logs are not opened.)
- [x] Custom recording formats through extensible readers. (Compiled in-process registrations with a documented example reader.)

## File Handling

- [x] Import recordings without unnecessary conversion.
- [ ] Support multiple simultaneously opened recordings. (Several files merge into one log under /LogN prefixes, aligned on the first enabled timestamp.)
- [x] Preserve original timestamps and metadata.
- [x] Recognize available schemas automatically when possible.
- [x] Support recordings containing multiple message types.
- [ ] Handle recordings with evolving or inconsistent schemas. (Struct and protobuf schemas are read from the log. Mid-file schema changes are not a supported feature.)
- [ ] Handle partially corrupted or incomplete recordings. (Decode failures mark the source as an error. There is no repair or partial-open recovery.)
- [x] Support compressed recordings.
- [ ] Support large recordings without loading everything into memory. (WPILOG field bodies decode on demand after a full-file read. Other formats decode entirely.)
- [ ] Allow selective loading of topics, channels, or time ranges. (WPILOG field bodies load when requested. Import cannot be limited to a time range.)
- [ ] Provide clear diagnostics for unsupported data. (Unknown extensions and worker failures mark the source as an error. Unsupported fields are not explained one by one.)
- [ ] Allow users to inspect undecoded data. (Raw values can be stored and exported. There is no binary or hex inspector.)
- [ ] Support user-provided schemas when automatic decoding is unavailable. (Schemas come from the log or built-in parsers. Users cannot register a schema in the UI.)

# 4. Universal Telemetry Representation

## Core Data Model

- [x] Common internal representation for telemetry.
- [x] Timestamped data samples.
- [x] Hierarchical topics and namespaces.
- [ ] Source identification. (NetworkTables and Driver Station fields use NT: and DS: prefixes. Merged files are grouped as /LogN.)
- [x] Schema and type metadata.

- [ ] Coordinate frame metadata. (A global coordinate-system preference converts poses. Frames are not stored per sample.)
- [x] Support for multiple timestamp domains. (Samples retain log, receive, or named-clock timestamps with explicit display conversions.)
- [ ] Preservation of original message data where practical. (Raw samples are retained for raw and some structured inputs. MCAP export drops raw samples.)
- [x] Support for both structured and unstructured data.

## Supported Data Types

- [x] Booleans.
- [x] Integers.
- [x] Floating-point values.
- [x] Strings.
- [ ] Enumerations. (The line graph interprets small sets of string or integer states as enum lanes. There is no enumeration log type.)
- [x] Arrays and lists.
- [ ] Maps and dictionaries. (JSON objects expand into nested fields. Maps are not a log type.)
- [x] Nested structures.
- [ ] Optional and nullable fields. (Missing samples are absent. Empty is only a placeholder for structured children.)
- [ ] Matrices. (Numeric arrays can be graphed element by element. Matrices are not a type.)
- [x] Binary data.
- [ ] Images. (No image sample type. Match video is a separate file, YouTube download, or The Blue Alliance clip.)
- [x] Point clouds. (ROS 2 PointCloud2 messages in MCAP and sqlite3 bags, displayed in the 3D scene.)
- [ ] User-defined data types. (WPILib structs, Photon structs, protobuf, MessagePack, JSON, and built-in schemas such as URCL. Users cannot register a type.)

## Schema Handling

- [x] Protobuf schema support.
- [x] ROS 2 message schema support. (CDR with `ros2msg` definitions in MCAP and sqlite3 bags. ROS 1 and IDL schemas are not supported.)
- [ ] JSON schema support where applicable. (JSON values are decoded. JSON Schema documents are not.)
- [x] Automatic nested field discovery.
- [x] Automatic extraction of graphable numeric fields.
- [x] Dynamic schema discovery.
- [ ] Schema changes during live sessions.
- [ ] Schema version compatibility. (RLOG revisions 1–2 and Road Runner revisions 0–1 are accepted. There is no general schema-version policy.)
- [x] User-defined schema registration. (Source-level in-process API. No UI or runtime loading.)
- [x] Extensible serialization decoders. (Custom binary schema decoders register through the public in-process API.)
- [ ] Clear handling of unknown or unsupported fields. (Unknown structured input can remain raw. Field-level failures usually go to the developer console.)

## Semantic Interpretation

- [ ] Recognize common robotics data structures. (WPILib poses, trajectories, Mechanism2d, joysticks, and swerve states drive the specialized tabs.)
- [x] Interpret poses, transforms, vectors, and rotations.
- [ ] Interpret joint states. (WPILib Mechanism2d ligament angles and lengths. Not general joint-state messages.)
- [ ] Interpret trajectories and paths. (WPILib Trajectory plus swerve and differential samples on the 3D field.)
- [ ] Interpret images and spatial sensor measurements. (AprilTag poses, vision targets, ROS 2 laser scans, and point clouds. Images are not interpreted.)
- [ ] Support custom semantic type mappings. (Object type is chosen per field in the 2D and 3D tabs. Mappings are not reusable semantic adapters.)
- [x] Allow users to override incorrect automatic interpretations.
- [x] Allow equivalent data from different formats to use the same visualizations.

# 42. Architectural Goals

These are architectural outcomes rather than prescribed
implementation methods.

- [x] Keep data ingestion independent of visualization.
- [ ] Keep communication protocols independent of serialization. (RLOG and Foxglove use separate frame transports. NetworkTables still combines transport and decoding.)
  - [x] Deliver RLOG TCP frames and Foxglove WebSocket messages through transports that do not decode telemetry.
- [ ] Keep serialization independent of semantic interpretation. (Decoders produce a Log. WPILib type strings then select field, mechanism, and swerve views.)
- [ ] Keep semantic interpretation independent of rendering. (Controllers interpret log types and renderers draw the result. The split is per tab, not a shared semantic layer.)
- [ ] Allow multiple formats to represent equivalent telemetry. (Supported logs and live sources feed one Log, so the same tabs apply.)
- [ ] Allow live and recorded sources to expose equivalent capabilities. (Same tabs. Phoenix and low-bandwidth live modes omit inactive fields, and some formats are desktop-only.)
- [ ] Preserve raw data even when semantic interpretation is unavailable. (Unrecognized payloads can remain raw.)
- [ ] Avoid assumptions about robot type or hardware. (Robot-state keys, swerve, joysticks, and field assets assume FRC or FTC robots.)
- [ ] Avoid assumptions about field dimensions or coordinate conventions. (Field assets carry fixed dimensions. Coordinate choices are the built-in FRC and FTC conventions.)
- [ ] Avoid assuming a single robot or single processing computer. (One live connection at a time. Multiple poses can still be drawn.)
- [x] Avoid assuming all timestamps share one clock. (Samples retain their original domain. The timeline names its display clock, and NetworkTables applies an explicit cursor conversion.)
- [ ] Avoid assuming a particular telemetry update frequency. (Graphs accept irregular timestamps. Paused stepping falls back to 0.02 s without AdvantageKit timestamps.)
- [x] Allow additional recording formats without redesigning visualizations.
- [x] Allow additional protocols without redesigning telemetry processing.
- [ ] Allow additional semantic types without changing data transports. (New WPILib-style structs decode without a new transport. New visual meaning usually needs a tab or object type.)
- [x] Allow additional visualizations without modifying data sources.
- [ ] Enable headless operation for relevant functionality. (AdvantageScope Lite is still a UI. There is no headless recorder or analysis tool.)
- [x] Support both streaming and random-access data.
- [ ] Support analysis of incomplete or partially decoded data. (WPILOG can show fields before every body is decoded. A failed file does not open partially.)
- [ ] Support configurable performance and memory tradeoffs. (3D quality settings and the live discard window.)
- [x] Avoid unnecessary duplication of existing AdvantageScope functionality.
- [ ] Favor interoperability with established robotics standards. (WPILOG, NetworkTables 4, protobuf, glTF, and MCAP export. ROS, DDS, and generic MCAP import are absent.)
- [ ] Keep architectural decisions open to revision as requirements evolve.

# 43. Long-Term Success Criteria

TerraScope should eventually allow users to:

- [ ] Open recordings from different robotics frameworks in one application. (WPILib, AdvantageKit, CTRE Hoot, REV, Road Runner, FTC-related logs, CSV, and Driver Station logs.)
- [ ] Connect to arbitrary robots without requiring WPILib or ROS. (CSV, RLOG, and generic numeric fields. Live connections are NetworkTables, RLOG, Phoenix, or FTC Dashboard.)
- [ ] Inspect structured telemetry without writing custom parsers. (Structs and protobuf decode when the log carries a schema.)
- [x] Graph numerical telemetry immediately.
- [x] Visualize robot motion and mechanisms.
- [ ] Visualize camera, LiDAR, and other sensor data. (AprilTags, vision targets, and separate match video. No LiDAR or in-log images.)
- [x] Reconstruct historical robot state.
- [ ] Correlate software behavior with physical robot behavior. (Console messages and robot poses share the timeline.)
- [ ] Diagnose localization and navigation problems. (Pose, vision, AprilTag, and trajectory views. No covariance, costmap, or error metrics.)
- [ ] Diagnose actuator and control problems. (Graphs plus REV, URCL, and Phoenix motor fields. No controller-contribution view.)
- [ ] Identify communication and timing problems. (NetworkTables latency and Driver Station logs. No general loss or delay detector.)
- [ ] Analyze distributed robotic systems.
- [ ] Compare experimental and competition runs. (Merge logs, then plot or overlay fields.)
- [ ] Record and replay telemetry without custom infrastructure. (Playback and export are built in. Continuous recording is not.)
- [ ] Automate repetitive analysis workflows.
- [ ] Develop custom visualizations without modifying the application core.
- [ ] Share useful debugging workflows with other developers. (Layout JSON can be exported and imported.)
- [x] Use the same application for simulation and physical robots.
- [ ] Use the same application for robotics and general engineering data. (CSV and line graphs. Most views assume robot structures.)
- [ ] Integrate telemetry with minimal modifications to existing software. (Existing WPILOG and NetworkTables publishers work unchanged.)

# Final Objective

TerraScope should be a universal environment for observing,
recording, visualizing, analyzing, and understanding complex
engineering systems.

A user should be able to connect a robot, open a recording,
inspect every available signal, visualize its behavior, and
understand what happened without needing to know which software
framework generated the underlying data.

The platform should support everything from simple microcontroller
projects to complex distributed autonomous systems.

TerraScope should preserve the accessibility and powerful
visualization experience of AdvantageScope while expanding its
capabilities into a general-purpose engineering platform.

The defining principle:

"Any robot. Any framework. Any data. One scope."
